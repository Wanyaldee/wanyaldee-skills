# ADRの書き方

ADRは「何をしたか」だけでなく「なぜそのコードが存在するか」を記録する。
6節、この順序で: **Context(経緯)、Decision(決定事項)、Reason(理由)、
Alternatives rejected(却下した代替案)、Consequences(影響)、
Verification(検証)。** Reason は省略・誤魔化されがちな節 —— この
スキルの大半はこの節についてのものである。

## いつ書くか

- 非自明な作業(新機能、アーキテクチャ選択、依存追加、スキーマ変更、
  将来の読者が「なぜこうなっている?」と聞くもの)の完了後。
- 自明な修正(typo、明白な1行)にADRは不要。
- `docs/adr/NNNN-title.md` として、既存の最大番号から連番で保存する
  (ディレクトリがなければ作成)。リポジトリがすでに `docs/adr/en/` +
  `docs/adr/ja/` の相互リンク方式を採用しているならそれに従う。
  そうでなければ単一ファイルでよい。

## 6つの節

### Context(経緯)

この作業が持ち上がった状況・問題。以前は何が真だったか、何が
未解決だったか。

### Decision(決定事項)

実際に何をしたか。差分を読まなくても仕組みが分かる粒度で書く。

### Reason(理由)—— なぜこのコードなのか

Decision の言い換えではない。Decision は「何をしたか」、Reason は
「なぜ他のやり方(それも一応"動く"やり方)ではなくこの形なのか」を
答える。

**必須: 実際のコード(または要となる抜粋)をコードブロックとして
貼り、その上でコード中の選択 —— 具体的な値、アルゴリズム、順序、
使用ライブラリ —— を、読者が当然抱く疑問に対して説明する。**
識別子の名前だけ挙げて(「リトライループが」「タイムアウトの値が」)
コードを示さない散文は、読者に正当化対象のコードを再構築させてから
その正当性を判断させることになる。

**アンチパターン —— あやふやな説明。** 以下の言い回しは Reason 節から
禁止する。ほとんどどんな実装に対しても言えてしまい、このコード固有の
説明になっていないため:

- 「信頼性のため」「パフォーマンス向上のため」「堅牢性のため」
- 「エッジケース対応のため」「UX向上のため」
- 「これが標準的な/ベストプラクティスなやり方だから」

どれも理由の代用品であって理由そのものではない。テスト: その文を
**別の**PRの**別の**コードに貼り付けても違和感なく通用するか?
通用するなら、このコードについては何も説明していない。

**この基準がある理由:** AI支援によってコードを書くことはほぼ無償に
なった。しかしコードを**理解する**ことまで無償にはなっていない。
関係者の誰も説明できない変更は、誰も安全に変更・デバッグ・
責任を持てない変更である —— 数ヶ月後の本人自身も含めて。Reason 節は
その理解を言葉として強制的に書き出す場所であり、コードを説明の隣に
置くことで両者を突き合わせて検証できるようにする。

**悪い例**(もっともらしい散文だが、コードがない —— よくある失敗
パターン):

> Reason: `requests.get` は不安定なネットワークで一過性に失敗しうる。
> 指数バックオフ付きの有界ループはサーバーを叩き続けずにそれを
> 吸収する。

**良い例**(同じ理由付けだが、コードを掲載し、具体的な選択1つ1つに
説明を付す):

```python
def fetch_with_retry(url, max_attempts=5):
    for attempt in range(max_attempts):
        try:
            return requests.get(url, timeout=5)
        except requests.RequestException:
            if attempt == max_attempts - 1:
                raise
            time.sleep(2 ** attempt)
```

- `except requests.RequestException`(素の `except` ではない): ネット
  ワーク/HTTP起因の失敗のみに絞り、呼び出し側コードのバグまで
  黙ってリトライしないようにするため。
- `2 ** attempt` のバックオフ(固定遅延ではない): 5回とも固定1秒
  遅延だと、不調なサーバーを一定レートで叩き続けてしまう。指数
  バックオフなら合計待ち時間を約31秒に抑えつつ、後になるほど強く
  間隔を空けられる。
- `max_attempts=5`(無制限ではない): 死んでいるエンドポイントは
  無限リトライではなく約31秒で失敗するようにするため。
- 最終試行での `raise`(黙って `None` を返さない): 戻り値が `None`
  かどうかで判定する呼び出し側は、本物の障害を「空の結果」と
  誤認しかねないため。

### Alternatives rejected(却下した代替案)

各1行、具体的な却下理由付きで。理由なしの「Xも検討した」は
エントリとして認めない。

### Consequences(影響)

今後何が楽になり何が難しくなるか。既知の限界 —— 意図的に残した
近道(ショートカット)を含む。

### Verification(検証)

実際に何を実行して確認したか —— そして何を**検証していないか**。
「Xのため未実施」は正直な有用な1行であり、告白ではない。

## 言い訳と実態の対応表

| 言い訳 | 実態 |
|---|---|
| 「散文で既に説明した、コードは冗長」 | 散文は言い換えにすぎない。読者が突き合わせて検証すべき対象はコードそのもの。両方が並んでいて初めて検証できる —— 怠慢でなくても Reason 節があやふやに読める最大の原因はこれ。 |
| 「Decision節で既に差分を見せている」 | Decisionは「何をしたか」、Reasonはコードの隣でその各部分を正当化する場所。分離すると、読者は正当化を読む頃にはコードを見失っている。 |
| 「明らかに標準的なパターンなので説明不要」 | 標準的ならその旨を1行、続けて非自明な選択(具体的なタイムアウト値、具体的な順序)を1つ名指しすればよい。10秒の手間で「標準的なパターン」よりはるかに価値がある。 |
| 「AIが正しく書いたので、なぜかを再導出する必要はない」 | 正しさと理解は別物。今説明できなければ、後で安全に変更できず、今この時点でも責任を持てない。 |
| 「小さな変更だから」 | 小さくて自明ならそもそもADR不要(「いつ書くか」を参照)。ADRを書くに値したなら、本物のReason節を書くに値する。 |

## クイックリファレンス

| 節 | 答えること |
|---|---|
| Context | 以前は何が真だったか、何が未解決だったか |
| Decision | 何をしたか、その形 |
| Reason | なぜ**この**コードなのか —— コード掲載、選択ごとの説明 |
| Alternatives rejected | 他に何を検討し、なぜ却下したか、各1行 |
| Consequences | 何が楽になり何が難しくなるか、既知の限界 |
| Verification | 実際に何を実行したか、何を検証していないか |
