# メモリ規律 — 和訳

> 人間用の参考訳。Claude が読み込むのは [SKILL.md](SKILL.md)(英語版)のみ。編集は英語版が先、和訳が追随する。
>
> description 訳: 永続オートメモリ(memory/*.md + MEMORY.md 索引)の書き方と保守の規範。教訓・好み・決定・プロジェクト事実をメモリに保存するとき、既存メモリを更新・整理するとき、想起されたメモリがコードや環境の現状と矛盾しているときに使用。

メモリは将来のセッションが信頼できて初めて役に立つ。ここの各規則は、実際のメモリ監査(2026-07-04)で違反が観測されたものに対応している: リポジトリと重複する仕様書丸写し、索引から漏れたファイル、書いたその日に嘘になったメモリ。

## 入れるもの

- 耐久的な事実と揮発的な状態を1ファイルに混ぜると部分的に腐る — 分割する。揮発的な状態(進捗、検討中の決定)は**書き換えられる前提**の専用ファイルにする。
- 未確定事項も保存する価値があるが、**担当者付きでのみ** — 「待ち: 岡田さんがXを確認中」。誰が解決するかとセットで記録された未解決点は一級の事実。
- 既に `docs/` にある仕様・設計・計画は、コピーせずポインタと非自明な差分だけを置く。丸写しが上記の「仕様書丸写し」の失敗そのもの。

## フォーマット

```markdown
---
metadata:
  origin: <model-id>, <YYYY-MM-DD>
---
```

ハーネス自体のテンプレートに対して増える項目は1つだけ: `origin`。セッションIDはログが削除されると追跡不能になるが、frontmatter は消えない — だからモデル名と絶対日付を直接記録する。日付はプロジェクトメモリに限らず、すべて絶対表記にする。

## 索引

`MEMORY.md` の1行は、メモリファイルを書いた**同じターンで**追加する。後回しにはしない — 未索引のメモリは決して想起されない。ダッシュの後のフックは、内容の予告ではなく「そのファイルを開く理由」として書く。

## 保守 — 同一セッション則

直前に観測した事実と矛盾するメモリは、**気づいたそのセッション・そのターンで**直す — 「あとで直す」印を付けて放置しない。陳腐化したメモリは無いより悪い: 信頼された上で間違っている。

履歴が重要なら日付付き訂正を追記し、不要なら書き直す。置き換えられた計画は、置き換えた側のドキュメントへのポインタに縮める。

保存前に、そのトピックを既にカバーするファイルが索引にないか確認する。
