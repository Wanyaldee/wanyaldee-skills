# 0016: 明示パスの `rm -rf` を、一律拒否から確認付き許可へ

(English: [0016-rm-rf-explicit-path-ask.md](../en/0016-rm-rf-explicit-path-ask.md))

## 背景 (Context)

ADR 0009 は、再帰フラグと強制フラグの両方を持つ `rm` を無条件にブロックした。
そのとき「削除対象の分類はシェル文字列に対して脆い」として対象ベースの判定を
却下し、代わりにフラグの組み合わせでブロックする道を選んだ。理由は「`-f` の
無い `rm -r` が正当なクリーンアップ用に残るから」だった。

この見込みは実際には成立しなかった。ユーザーから、通常のクリーンアップで
このブロックが何度も発火するとの報告があり(名指しされた例は完了済みの git
worktree)、明示的なディレクトリを指定した再帰削除を確認の上で許可したい、
との要求が出た。`rm -r` は ADR 0009 が想定した逃げ道になっていない。worktree や
`node_modules` ツリーでは保護されたファイルごとに確認を求めてくるため、結局
ブロックされる形が使われ続ける。

`dev-philosophy` §3 の明文は「`rm -rf` などの破壊的コマンドの全面禁止」である。
本 ADR はその禁止を「対象が事前に判明しない場合」に狭める。哲学ドキュメントは
依然として絶対的な書き方のままで、ここでは変更しない。整合させることは提案に
とどめる。

## 決定 (Decision)

`hooks/deny-bash.py` は、再帰+強制の `rm` に対して常に拒否するのをやめ、
次の3つの結果のいずれかを返す。

- **ask** — すべてのオペランドが、保護対象でないリテラルなパスである場合。
  Claude Code がパスを示してユーザーに確認を求め、ユーザーが承認または拒否する。
  バージョン 2.8.0(ADR 0015 と同時リリース)。
- **deny** — いずれかのオペランドが、グロブ、`$`/バッククォートの展開を含む、
  `.` または `..`、`/`・最上位パス・ホームディレクトリ・保護ディレクトリの完全一致・
  システムルート配下のいずれかに解決される場合。あるいはオペランドそのものが
  読み取れない場合(引用符の不整合、オペランド無し、`xargs`/`find -exec` 経由)。
- 1つのコマンド行に両方が現れた場合は deny が勝つ。ask は記録だけしておき、
  すべての deny 規則を通過した後にのみ出力するため。

新規のエッジケーステストにより、既存の穴が別途1件見つかり修正した。セグメント
判定がパス付きのバイナリを認識しておらず、2.2.0 から 2.7.0 までのフックでは
`/bin/rm -rf /` が**許可**されていた。

## 理由 (Reason) — なぜこのコードなのか

肝はオペランド分類器である。

```python
def unsafe_target(tok):
    if any(g in tok for g in ("*", "?", "[")):
        return f"'{tok}' is a glob, so what it matches can't be known here"
    if "$" in tok or "`" in tok:
        return f"'{tok}' contains variable or command substitution"
    if tok in (".", ".."):
        return f"'{tok}' is the current or parent directory"
    expanded = os.path.expanduser(tok)
    if expanded.startswith("~"):
        return f"'{tok}' has a ~ reference that doesn't resolve here"
    path = os.path.normpath(os.path.join(cwd, expanded))
    if path in PROTECTED_EXACT:
        return f"'{tok}' resolves to {path}, a protected location"
    if path == home:
        return f"'{tok}' resolves to the home directory"
    if path == "/" or any(path == r or path.startswith(r + "/") for r in SYSTEM_ROOTS):
        return f"'{tok}' resolves to {path}, inside system-owned state"
    if len([p for p in path.split("/") if p]) < 2:
        return f"'{tok}' resolves to {path}, a top-level path"
    return None
```

- **グロブと `$`/バッククォートの判定を、パス解決より前に置いた。** 確認を挟む
  前提は「ユーザーがプロンプト上のパスを読んで判断できること」である。
  `rm -rf $BUILD_DIR` がユーザーに見せるのは変数名であって行き先ではないので、
  確認しても形だけになる。これが ADR 0009 の「脆い」という反論への直接の答え:
  脆いケースは推測せず、拒否する。
- **`os.getcwd()` ではなく、フックのペイロードにある `cwd` を使って
  `os.path.normpath(os.path.join(cwd, expanded))` する。** フックのプロセスは
  必ずしもセッションの作業ディレクトリで動くとは限らず、`../old-worktree` の
  ような相対オペランドは基準が正しくなければ意味を成さない。ここを誤ると
  `../..` が別の祖先に解決され、分類を誤る。
- **比較の前に `normpath` する(後ではなく)。** `build/`、`./build//sub`、
  `../..` を、保護パス集合が書かれている形に畳む。生のトークンを比較すると
  `"/etc/"` や `"foo/../.."` が集合の判定をすり抜ける。
- **`PROTECTED_EXACT` は完全一致、`SYSTEM_ROOTS` は前方一致。** リスクの質が
  異なるためである。`/var` は削除されてはならないが、`/var/lib/myapp/cache` は
  ただのアプリケーションデータで、まさに今回の変更が解放しようとしている
  クリーンアップそのものである。`/usr` は違う。その配下にユーザーが消してよい
  ものは無いので、サブツリーごと拒否する。
- **パス構成要素が `< 2` で拒否(`< 1` ではない)。** `/data` はこのリストが
  知らない最上位ディレクトリであり、未知の最上位ディレクトリはスクラッチ用より
  マウントポイントである可能性が高い。`/data/scratch` は2要素なので ask になる。
- **`.` と `..` は解決前にトークンとして弾く。** `rm -rf .` は一見普通の深い
  パスに解決され、以降のチェックをすべて通ってしまうが、実行中のセッションの
  足元のディレクトリを消すことが意図であることはまず無く、しかもプロンプトの
  文面からは何が消えるか見えない。
- **この関数は真偽値ではなく文を返す。** その文字列がそのまま拒否理由になるので、
  ユーザーは「またブロックされた」ではなく、どのオペランドがなぜ駄目なのかを
  知らされる。この ADR を生んだ失敗そのものへの対処である。

ADR 0009 の判断を覆すことを正当化しているのは、誤分類したときの帰結である。
ADR 0009 は対象分類を **allow** のゲートとして評価していた。そこでは判定漏れが
無言のデータ削除になる。今回は分類が **ask** のゲートである。誤って通した
パスの最悪ケースは、ユーザーが却下する確認プロンプトが1つ出ることでしかない。
人間がクリックしない限り、何もファイルシステムには届かない。

`xargs`/`find -exec` 経由をグロブと同じ理由で拒否のまま残した。

```python
    if indirect:
        deny(
            "rm -rf fed by xargs/find -exec blocked: the paths come from another "
            "command, so they can't be shown before deletion. ..."
        )
```

パスは実行時にしか存在しないので、ユーザーの前に出せるものが何も無い。

## 却下した代替案 (Alternatives rejected)

- **確認を挟まず単に許可する** — 不可逆操作に人間の意思を介在させるという
  `dev-philosophy` §2 の要求から人間を外すことになる。ユーザーの要求も
  「確認の上」であり、無条件許可ではない。
- **拒否のまま残し、ユーザーが `!` で削除を実行する運用を続ける** — それが
  今回の苦情を生んだ現状そのもの。
- **ディレクトリ名の許可リスト(`node_modules`, `build`, `dist`, worktree パス)**
  — 次に出てくる未収載のケースでまた止まるし、名前ベースのリストはその
  ディレクトリが実際にどこにあるかを何も語らない。
- **`os.path.realpath` でシンボリックリンクを解決する** — `/etc` を指す
  シンボリックリンクを捕まえられるが、フックは実行前に動くため、判定のために
  ファイルシステムを読むと、判定時点と削除時点の間で変わりうる状態に結果が
  依存する。確認プロンプトが示すのはユーザーが書いたリテラルなパスであり、
  それこそがユーザーに検証できるものである。天井として記録する。
- **`.env` と DB の規則も併せて緩める** — 要求されていないし、どちらも
  誤検知の報告が出ていない。

## 影響 (Consequences)

- 完了済み worktree、ビルドディレクトリ、`node_modules` ツリーの掃除が、
  確認1回で済むようになった。従来はユーザー自身がコマンドを実行する以外に
  手が無かった。
- `/bin/rm -rf /` が、Bash フック導入以来はじめて拒否されるようになった。
  2.2.0 から 2.7.0 までのセッションでは実行可能だった。
- 既知の天井: シンボリックリンクのオペランドはリテラルなパスで分類されるため、
  システムディレクトリを指す `build` という名前のリンクは `build` として
  確認プロンプトに出る。そこでの検査役はユーザーである。
- 既知の天井(ADR 0009 から不変): これは事故防止のガードであり、敵対的境界では
  ない。Python スクリプトによるツリー削除は今も通る。
- `dev-philosophy` §3 は依然として `rm -rf` の全面禁止を述べており、機構と
  哲学ドキュメントが食い違う状態になった。提案(未実施): 当該行を「破壊的
  コマンドは確認を必須とし、対象を事前に提示できない場合は拒否する」に緩める。
- テストマトリクスは本セッションのスクラッチパッドにあり、リポジトリには無い。
  このパッケージにテストディレクトリは存在せず、新設は今回のスコープ外とした。
  ケースは本 ADR の検証節に件数と分類で記録する。

## 検証 (Verification)

- 変更前のベースライン: 46ケースのマトリクスで35件通過、11件失敗。失敗11件は
  すべてユーザーが報告した明示パスのケースで、いずれも deny を返していた。
- 変更後: 46/46 通過。第2のマトリクス26ケースは、1行に両方が現れたときの
  deny 優先、フラグの綴り(`-fr`, `-r -f`, `-rfv`, `--recursive --force`, `--`)、
  パス付きバイナリ、末尾および重複スラッシュ、深いシステムパス、引用された
  危険な対象、改行区切りスクリプト、空コマンドを網羅する。初回実行で26件中
  1件失敗し、それがパス付きバイナリの穴を検出した。修正後は26/26 通過。
- 修正後に両マトリクスを再実行し、72ケース中72ケース通過。
- パス付きの3形態を手動で確認: `/bin/rm -rf /` と `/usr/bin/rm -rf /etc` は
  deny、`./scripts/rm -rf build` は ask。
- 未検証: `ask` の判定を実際の Claude Code セッションで端から端まで観測して
  いない。確認しているのはフックの JSON 出力までである。理由の文字列が
  プロンプトに意図どおり表示されるかは未確認。
